# 码脊 CodeSpine —— AI 语义分析规则（ANALYSIS）

> 你的角色：把 `spine-raw.json`（确定性 diff 骨架）转化为 `spine.json`（评审视图数据）。
> **铁律：骨架层是事实。行号、调用关系、方法边界只能引用 raw 中已有内容，禁止编造；不确定就降低置信度或标 refOnly。**

## 输入 / 输出

- 输入：`codespine ct` 产出的 `spine-raw.json`（文件/hunk/行级 diff + 新侧内容快照）
- 输出：符合 `SCHEMA.md` 的 `spine.json`，随后必须通过 `codespine audit`

## 分析七步

1. **diff 解读**：每个文件判断 变更类型（新增类/修改类/字段配置类），统计方法级变更（签名行在 diff 内 = 新增方法，否则 = 修改）。
2. **入口溯源**：从每个变更类**向上遍历调用方，直至 HTTP 入口（Controller/路由），最深允许 7 层**。每一跳必须逐跳验证（在 raw 内容快照里确认调用点存在），**禁止凭"业务上应该相关"挂链**。找不到入口的进特殊链路。
3. **链路组织**：入口 → 未变更中间层（薄委托/编排层）→ 变更类。未变更中间层保留为节点，标注 `callLines`（≤3 行关键调用，含行号与下一跳）。
4. **逻辑块切分**：每个变更方法拆 3~6 个语义块；块名 = **动宾短语 ≤8 字**（如"保存前重核权益"）；每块带 `range`（行区间，来自 raw hunk）、`desc`（一句话）、`via`（向上调用路径，每跳含调用行号）、`snippet`（3~5 行关键代码，含真实缩进）。大方法（>50 行或 >6 块）允许一层 phases 分组。
5. **入参对象**：入口的参数 DTO 有字段级变更时，建 `params.objects`（嵌套位置 + 字段 + `+/−/~` 类型 + 说明）。
6. **覆盖率闭包**：`变更文件全集 − 已挂链文件 = 差集`，写入 `orphans`（含原因分类：非调用引用/无上游入口等）与 `coverage.inventory`（全量文件索引：每个文件在哪条链的什么位置——**任何变更不允许静默丢失**）。
7. **自检**：产出后逐块核对——via 每跳的行号回读内容快照、snippet 行号与文本一致、in 标注的方法确实包含 range。**行号必须机器回读，不靠记忆。**

## 排序与去重规则

- **块排序 = 逻辑推进序**：排序键 = `[via 各跳调用行号..., 自身起始行]` 字典序（深度优先执行顺序）。被调函数的块排在其被调用点之后，不是文件物理行序。
- **枢纽去重**：同一类在一条链中第二次出现 → `refOnly: true`（引用芯片，首次才展开）。
- **跨链复用**：编辑链复用创建链的类 → refOnly + badge "复用创建链"。

## 表达规范

- 所有方法引用带归属前缀（`Support.isSpecialField`，避免同名混淆）
- 未变更节点在"只看脊痕"模式下要么是 ≤3 行调用行的轻量卡，要么是折叠药丸
- 说明文案：块 desc 一句话；入口/出口条带业务语义；`generatedBy` 注明分析方式

## 禁止事项

- 禁止编造行号 / 虚构调用边 / 语义挂链（"看起来相关"不算调用）
- 禁止把删除的配置文件混进链路节点
- 禁止在骨架层使用"大概/可能"——不确定属于语义层，用置信度表达
